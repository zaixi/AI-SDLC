# 项目背景、痛点与需求

更新日期：2026-10-28。本文是 AI-SDLC 后续选型、设计和迭代的需求入口，汇总用户已明确的目标与约束。研究报告和评测提供依据，不自动成为需求或实现决定。

## 为什么做这个项目

公司已有 AI 辅助写代码和 AI 评审 Gerrit，但用户感到这些环节割裂：代码生成增加，人对系统的理解、评审和维护能力却没有同步跟上。已有项目通常也没有完整的设计文档可供 AI 使用。

用户还明确要求：新功能或新框架应从最开始设计时就适配 AI 原生编程，使后续理解和维护更准确、更简单。范围同时覆盖存量系统的理解与改善，以及新增能力的前期设计；两者都需要考察后续修改和维护。

用户希望优先采用现成的 AI 原生研发实践，少量补充，形成可以持续迭代、跨 Agent 使用的工作方式。核心目标是提高人和 AI 对系统及变更的理解、评审与维护能力；代码生成量不是本项目的成功标准。

最初分享会话中的用户陈述见 [痛点摘录](../materials/reviews/Shared-conversation-pain-points.md)。该文件记录了当时的读取方式和归纳边界；本次未重新访问分享页面。后续明确要求来自本项目对话，下文保留关键原话供追溯。

## 要解决的痛点

| 痛点 | 需要达到的结果 | 依据 |
|---|---|---|
| AI 生成代码越来越多，人越来越难维护和评审 | 变更能说明目的、影响与验证依据，使人能判断而非只能相信生成或评审结论 | 原始痛点摘录中的代码维护与评审陈述 |
| ADR 和 contexts/ 已留下，但长篇、零散、英文文字仍难形成系统理解 | 人能看懂系统结构、边界和关键关系；保留必要细节，并提供合适的图解和中文说明 | 原始痛点摘录中的 ask-matt 使用反馈 |
| AI 能过滤低级问题，但人工应关注什么、如何发现高价值问题尚不清楚 | 评审能检查与变更相关的设计意图、约束和取舍，并指出证据与未知项 | 原始痛点摘录中的 Review 问题；具体检查方法尚待确定 |
| 存量项目缺少成套文档，理解、质量和维护缺乏支撑 | 能从现有代码和资料开始，补出必要的隐性知识；不以先建完整文档体系为前提 | 原始痛点摘录中的已有项目维护问题 |
| 新功能或新框架从设计阶段就需要考虑 AI 后续参与理解和维护 | 设计能让后续的人和 AI 准确理解意图、边界和约束，容易定位、修改并验证行为；不能只评价第一次生成是否成功 | 本项目对话：“一个新功能或者新框架怎么从最开始设计时就能适配 ai 原生编程，让后续的理解和维护更准确和简单” |
| AI 输出冗长，套话多，同一概念解释多遍 | 删除重复和无信息内容，保留有效信息与必要解释；不能靠删掉条件、例外或不确定性缩短 | 本项目对话：“AI 的输出经常又臭又长，实际的信息并不多，很多都是套话，或者一个概念解释几遍” |
| 代码更新后，相关文档没有同步更新 | 每次变更检查已有设计说明、契约和图是否受影响；更新当前有效内容，改变决定时保留历史理由，避免让错误实现反向覆盖约定 | 本项目对话：“代码更新过程中，代码更新了，文档没有同步更新” |
| 背景和需求留在会话中，后续迭代容易丢失 | 换会话或 Agent 后，仍能查到为什么做、要解决什么、已有约束与决定 | 本项目对话：“以后迭代的时候会丢失背景” |
| agent 总喜欢自己造轮子，不借鉴已有的成熟方案 | 新功能、选型、加依赖之前先查现成方案，再决定采用、扩展、借鉴还是自建；自建不被禁止，但要有查过的依据 | 本项目对话（2026-10-28）：“agent 总喜欢自己造轮子，不喜欢借鉴已有的成熟方案” |
| 老代码里的内容可能出于特殊原因或场景，原因只在原工程师脑子里；接手者的共识是尽量不改老功能和老代码，怕去掉或修改后有意想不到的后果 | 改动之前能查到它为什么在那；查不到时明确是“原因未知”，不当成“没用”，也不凭代码推断成原作者的决定 | 本项目对话（2026-10-28）：“过去人工写代码，一些内容在工程师脑子里，后续维护的时候自己知道，但是接手维护代码的时候，工程师的共识是尽量不改老的功能和代码(屎山代码)，它可能是某个特殊原因或者场景加的，去掉或者修改会有意想不到的后果” |

以上是需求归纳，不表示已经实现或验证有效。尤其是人工评审如何分工、如何保证质量，当前仍是待解决的问题。

## 用户已明确的要求

1. **优先复用，少量自建。** “不想从头自己搭建一套，想用现成的，再加少量自己写的，这样能够享受他们的更新。”先核对现成方案与缺口，再决定补充内容；保留上游来源和本地改动边界。
2. **不绑定 Agent。** 用户可能使用 Codex、Claude、OpenCode、Zed、Qoder 等。核心方法和知识应可迁移；客户端的安装、自动发现、工具与权限机制要分别核实，不能凭 Markdown 通用就宣称全面兼容。
3. **按知识价值记录。** “agent 从代码中很容易拿到的信息不需要形成 wiki/markdown，需要文档记录的是架构设计，约束，决策背后的原因等原来留在人脑中的东西。”代码可恢复的信息按需查询；长期记录意图、约束、理由和取舍，避免平行维护代码说明库。
4. **最终只有一个入口。** “我想最终只有一个入口，而不是人记很多 skill 来手动触发。”辅助 Skill 应由入口或任务按场景选择；统一主流程及客户端接入尚未完成。
5. **重视图解。** “图很重要，图比文字的可读性和信息量都大。”能用图帮助理解的内容应按需图解，覆盖设计之外的解释、评审、变更等场景。图解 Skill 的职责是表达，不承担整个 AI 原生研发流程或知识管理。
6. **精练但充分。** 中文表达应清楚、直接，减少套话和重复；复杂问题仍需保留足够依据与解释。具体术语、命令、代码和必要限定不能为润色而改义。
7. **适量验证，轻量入库。** 用户已要求每个组合通常两次或三次，不默认重复十次。保留可复用测试方法、案例、协议和脚本；大体积运行产物在仓库外保存，报告说明实际证据位置及验证范围。

## 从设计阶段适配 AI：后续研究的评价方向

用户确认的是“从一开始设计，就让后续理解和维护更准确、更简单”。下面是据此提出的评价问题，用于下一轮对比，尚未确定为架构规范、模板或必装 Skill：

- **意图可获取**：新会话能否找到目标、非目标、约束、取舍及其理由？
- **边界清楚**：能否从接口、类型和模块职责看清数据所有权、依赖方向与行为契约，避免依赖隐含约定？
- **改动影响可判断**：一个合理的小改动能否在有限范围内理解和完成？需要联动的调用方是否明确？不以文件越小、层越多作为好设计的标准。
- **正确性可验证**：关键不变量和边界是否有可以运行的检查？设计是否留下合适的测试边界与诊断信息，能发现看似正确的错误修改？
- **维护负担可控**：代码已经能表达的事实不再重复写 Wiki，无法恢复的原因有长期记录；新增抽象、文档和工具是否确实降低后续成本？

评价应包含第二次工作：设计并实现一个有限功能后，让新的会话或 Agent 理解并修改它，观察事实恢复、约束遵循、影响判断与验证情况。只评首次产物、篇幅或代码行数不足以回答该需求。具体案例和配置尚未选择，本次不运行评测。

## 主流程选型决定

**2026-10-15，用户确认：“那就选定 matt 吧”。** 采用 Matt Pocock Skills 作为主研发流程基础，保留已有 visual-explanation、humanizer 和 search-before-build 辅助能力。

选择理由：Matt 已有澄清、领域建模、规格、任务、实现和评审能力；`codebase-design` 关注接口承载的契约、复杂性封装、修改局部性与可测试性，覆盖新功能从设计开始便于后续维护的需要。其可组合方式也符合优先复用、少量自建的要求。比较依据见[机制比较](../materials/reviews/AI-SDLC-workflow-deep-comparison-20261015.md)及本次补核的 [codebase-design 原文](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/codebase-design/SKILL.md)。该提交是研究版本，正式接入时仍需记录实际采用版本。

本次确认基础方案，尚未确定安装范围、客户端接入方式或本地修改。pstack 的历史调查与设计方法继续作为缺口补充的参考；其他候选没有因此一并获准采用。后续先验证 Matt 原有能力，遇到实际缺口再决定补充，尽量保持上游可更新。

重点验证单入口能否正确调度、评审能否找到相关设计理由，以及新会话能否完成第二次修改。跨 Agent 支持需逐客户端核对；静态源码比较不等于任务效果验证。

## 下一步需要明确的内容

基础方案已选定，完整主流程尚未接入。接下来围绕 Matt 明确以下缺口：

- 选择存量项目变更，以及新功能或新框架从设计到后续修改的代表场景；Kernel、BSP、Safety、Robot 是此前举例，不是已选定目标。
- 用哪些现成能力衔接澄清、设计、实现、验证与评审；哪些痛点仍有实际缺口。上一轮助手提出的阶段划分只是建议，不是已批准架构。
- 人工评审聚焦哪些问题，哪些证据足以支持接受变更，哪些情况需要人作决定。
- 怎样用现有记录延续设计意图、约束与工作状态，同时避免另建冗长知识库。
- 单入口在不同 Agent 中如何接入，以及如何验证它会选择正确的辅助能力。

不预先把这些问题变成全部必须新建的 Skill、服务或文档模板。是否解决，应看真实任务中人能否理解、评审和接续工作，以及验证、返工和维护证据；回答更短、图更多或入口校验通过都不能单独证明主问题已解决。

## 需求澄清记录

- **2026-10-15：补齐前期设计目标。** 此前比较偏重存量代码、历史原因与评审，并建议优先用存量变更评估。用户明确补充新功能、新框架也要从设计时适配 AI，使后续理解与维护更准确、简单。因此后续选型同时评价“理解和改善已有系统”与“设计出便于未来维护的新能力”；此前静态比较仍可作部分依据，不能代表完整需求下的排序。
- **2026-10-28：补充两条痛点。** 用户补充：agent 倾向自己造轮子；老代码的原因只在工程师脑子里，接手者不敢改。前者与上文“优先复用”的要求相关，现有对应是 [search-before-build](../skills/search-before-build/SKILL.md)，它只做过五题单次实测，造轮子是否减少没有量化。后者与“存量项目缺文档”相关但不同：缺的是某段代码的原因，不是整套文档；pstack 的历史调查方法继续作参考，没有在真实的老代码上试过。同日加入 [人判断什么，证据怎么留](method.md)，是设计稿，不是已采用的决定。

## 后续如何维护这份记录

更改核心流程、引入新 Skill 或调整需求范围前，先读本文及相关来源。用户新确认的目标、约束或取舍更新在此；实现细节、实验轨迹和临时进度保留在对应位置，通过链接访问，不复制进本文。

改变已有决定时，记录日期、原决定、变更理由和依据，不静默覆盖。助手建议保持建议状态；用户确认或明确授权后再记为决定。早期资料中的“尚未安装”等表述描述当时状态，当前采用情况以本页及实际文件为准。

本页汇总已有证据，不声称完整复刻所有原始会话。用户补充或纠正痛点时，保留变更理由并更新相关内容。
