# 人判断什么，证据怎么留

状态：设计稿。内容精简自另一个仓库的方法稿 v0.8（2026-09-24），做过桌面推演和交叉评审，另有一次冷启动接手评估（n=1，见[评测报告](../evaluations/handoff/2026-09-24-cold-start/report.md)）。没有在真实任务中试运行，不代表已采用的决定。

本页只补 Matt 流程没有明说的判断规则，不修改 Matt 的任何 Skill。两者冲突时先记录，由用户决定，见 [project-intent](project-intent.md) 末尾的维护规则。完整原稿含 V 模型对应和场景推演，还没有归档到本仓库。

## 分工

- 人负责意图、价值判断、关键承诺和结果接受。
- agent 负责调查、提方案、控制细化深度、实现、验证和维护知识。
- agent 不能把自己的推荐、人的沉默或机械连答当成整体接受。一次整体授权只覆盖已展示的范围，不自动覆盖未展示的高影响取舍，也不自动授予发布或不可逆操作。

## 什么时候停止讨论

当再问一轮不会改变重要判断，而剩余细节能通过实现或实验解决时，agent 建议开工。进入实现前，当前增量要有：

- 共同认可的目标、范围、主要行为和重要限制；
- 关键行为和质量要求的判定办法，以及还缺哪些证据；
- 已分类的未知：实现中解决、实验后决定、阻塞相关工作，没有隐藏的高影响假设；
- 清楚的实施范围和权限。

连续讨论没有改变判断，或只是逐项接受推荐时，停止追加同类问题，改用具体结果或对比展示。轮数不设统一次数。

## 实现中发现新事实

| 发现 | 处理 |
| --- | --- |
| 局部算法或文件组织改变，承诺不变 | agent 自行选择、验证并更新说明，最终审阅展示重要差异 |
| 已接受的行为、公共边界或质量承诺无法保持 | 给出事实、影响、可选方案和推荐，等待必要决定；不受影响的授权工作继续 |
| 测试失败，判据可能有误 | 区分实现、环境、判据三类问题，依据原始要求查证，不能为通过而降低标准 |
| 环境不可用、预算耗尽或重复失败无新证据 | 保存实际状态和缺口，明确受阻，不宣称完整完成 |

## 证据

每份证据要回答：验证了哪项主张，针对哪个实际产物与环境，如何获得结果，覆盖什么、遗漏什么。

- 分支名或“测试通过”的摘要不能代表被测版本。
- 代码、要求、依赖或环境变化后，先判断哪些主张受影响，再更新相关证据；没受影响的可以复用。
- 多个 agent 同意不构成正确性证明；重要或难判断的变更增加独立取证。
- 测试答案不能只从生成的实现反推。

交付状态分四个维度表达，互相不能代替：

| 维度 | 取值 |
| --- | --- |
| 实现进度 | 未完成 / 完成 |
| 验证完整性 | 未取得 / 部分验证 / 已满足 |
| 人的接受 | 待审阅 / 需修订 / 已接受 |
| 发布情况 | 未发布 / 已发布 / 不适用 |

## 保留什么知识

门槛：省略后容易改错，或需要付出明显代价才能重新发现。包括关键不变量、假设、重要反例和未采用的方案；不保留全部推理、命令或代码的文字复述。能执行的约束尽量进测试和检查。

知识有生命周期：依据不足为暂定，依据和适用范围明确后为有效，前提受影响或有反证时转为待复核，重新取证后恢复、修订或被替代。下面三个判断分别维护，不能合成一个“有效”标记：

| 判断 | 依据 |
| --- | --- |
| 要求或决定是否仍适用 | 有效意图和授权决定，可以先于代码成立 |
| 当前实现是否符合 | 对照要求和实际行为，不能由“已接受设计”推出 |
| 验证结果是否仍适用 | 被测状态、判据、环境和变化影响；失效意味着需要补证，不自动证明实现错了 |

接手时从当前入口定位范围，核对实际状态，按影响读取理由、约束和证据，再提出并验证修改判断。缺少历史理由时可以调查和重新论证，但不能把推断伪造成原作者的决定。

## 怎么判断值得采用

评价同时看质量、人的负担和总交付成本，不以代码生成量为标准。缺少基线时先建观察记录，不宣称提升百分比。

接手评估：给新会话一个确实涉及既有约束的维护任务，不给原始聊天，允许使用文档、代码和工具；事先定好判据，避免按 agent 的答案评分。通过的依据是关键保证保持、受影响行为验证充分、必要知识同步、没有靠原作者补充隐藏背景。资料缺失导致无法完成，记为知识覆盖缺口，不归咎于接手者。

## 没有验证的

- 没有在真实任务中试运行，没有人工基线。
- 接手评估只有一次，三个请求由设计者选定，设计和判读由同一个模型完成。
- 与 Matt 各入口怎么衔接，没有逐项核对。
