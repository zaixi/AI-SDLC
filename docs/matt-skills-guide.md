# Matt Pocock Skills 使用速查

整理日期：2026-10-16。基于插件版本 1.3.1、上游提交 `49dd158d1076134a641b33efb035946536778336`。本文归纳已讨论的 16 个用户入口及衔接方式；选型背景见[项目背景、痛点与需求](project-intent.md)。当前已选定 Matt 为基础，完整主流程尚未接入。

## 1. 工作入口：不知道选哪个就用 ask-matt

| Skill | 什么时候用 | 作用 |
|---|---|---|
| `ask-matt` | 不知道该走哪个流程 | 根据目标和当前状态推荐入口或路线 |
| `grill-with-docs` | 有具体研发想法，需要澄清需求和设计 | 追问目标、边界和取舍，按需更新术语表与 ADR |
| `grill-me` | 通用讨论，不需要维护项目领域文档 | 澄清计划或想法，不保存术语表与 ADR |
| `wayfinder` | 目标很大，路径和关键决定还不清楚 | 建立跨会话的决策地图，逐步解决关键问题 |
| `improve-codebase-architecture` | 已有代码难理解、难测试或难修改 | 调查架构改进机会，给出前后对比图，选中候选后继续讨论 |
| `triage` | 收到别人提交的 Bug、需求或反馈 | 按项目配置澄清、整理问题并推进状态，使工作得到相应处理 |

这些入口处于同一层，但起点不同。`ask-matt` 是它们之上的导航：可以只记住它，直接描述问题。原版会推荐入口，不保证自动执行整条流程；用户主动调用的入口不能由其他 Skill 直接调用。

`triage` 与 `implement` 的区别：前者处理“这个问题接下来怎么办”，后者执行明确的任务。例如“导出很慢”需要先弄清复现条件和期望结果，才能交给实现流程。`to-tickets` 已生成的任务通常已经准备好，不应再经过 `triage`。

## 2. 交付：按规模选择路径

需要规格和任务拆分时：`to-spec → to-tickets → implement 或 implement-spec`。

| Skill | 作用 |
|---|---|
| `to-spec` | 将已经充分讨论的内容整理为规格，发布到配置的任务管理系统；不负责重新访谈或补猜需求 |
| `to-tickets` | 将规格、计划或讨论拆成可验证的任务，标明依赖关系；倾向贯穿必要层次的小功能切片 |
| `implement` | 实施明确的工作，在约定边界执行 TDD，完成后审阅再提交 |
| `implement-spec` | 按任务依赖图调度子 agent，在独立 worktree 实现，汇总到集成分支并审阅 |

小而明确的任务可以直接 `implement`，不必创建单独的规格和任务文件。`implement` 与 `implement-spec` 是两条实现路径，不是先后步骤；后者需要相应的子 agent 和 Git 工具能力。

常见衔接：

- 具体新功能：`grill-with-docs → 按需形成规格和任务 → 实现`。
- 大型新框架：`wayfinder → 关键决定清楚后 to-spec → to-tickets → 实现`。
- 存量架构改进：`improve-codebase-architecture → 选中候选并澄清 → 按规模进入交付`。
- 外部问题：`triage → 准备好的任务交给 implement`；信息不足时继续调查或澄清。

箭头表示工作衔接，不表示原版自动调用下一个入口。

## 3. setup-matt-pocock-skills：项目初始化

每个项目通常运行一次，配置任务管理方式、分诊标签和领域文档位置；约定变化后再调整。

首次使用建议主动运行。`ask-matt` 明确列出 setup 前提，但没有程序化的初始化状态检查；`grill-with-docs` 没有明确要求检查或提醒 setup，可能直接开始讨论，并按默认位置按需创建 `GLOSSARY.md` 和 `docs/adr/`。

## 4. handoff：交接未完成的工作

用于换 agent、工作目录、交给同事或分出侧面任务等需要可携带上下文的场景。规格描述“要做什么”，交接补充“做到哪里、试过什么、什么还没验证”。

它不替代长期设计记录。原版交接文件保存在临时目录，跨机器需要传递；同一客户端仅因上下文变长时，还应考虑继续当前会话或使用客户端的上下文压缩能力，不必每次都生成交接文件。

## 5. retro：复盘并提出改进

根据实际会话找出导航、自动检查、规则和工具方面的问题，按严重程度提出改进候选。例如反复漏掉机械错误，应考虑自动检查；找文件困难，可考虑必要导航。

它不等于自动生成一份经验教训文档。建议落实为检查、工具或必要记录后，才形成持久改善。改善代码结构主要使用 `improve-codebase-architecture`。

## 6. teach：让 AI 系统地教你

用于学习概念或技能，例如结合实际项目学习模块设计。支持跨会话保存教学状态；目标是帮助你学会，不只是把当前回答写得更长。

## 7. wait-what：当前回答没听懂时重新解释

可以在讨论或其他流程中主动触发，补上缺失背景、解释术语或换一种表达，之后继续原流程。它不是自动嵌入的步骤，也不要求解释更长。

原版采用简化技术英语，并使用项目术语。中文使用需明确语言要求。

## 8. to-questionnaire：向特定知情者获取答案

先确认问谁、需要哪些答案，再生成针对性问卷，由用户交给对方或在会议中使用。例如旧框架的历史限制只有原负责人知道，可用它整理需要求证的设计原因。

它不是一般的待答问题清单。自己尚未想清楚的问题继续澄清，需要查资料的问题做研究；答案在别人那里时才准备问卷。原版面向人；交给另一个 agent 时，应确保它拥有当前缺少的资料或访问能力，避免只是换个 agent 猜测。
