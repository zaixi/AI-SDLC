## 阿里：新手册最值得细读，但要分清实证、粗略统计与愿景

新找到的官方手册是 **68 页《AI Native 研发范式实践手册》**。用户先前上传的 **29 页《AI Native 研发体系建设与落地手册》** 署名雷鹏 / 数据智谷。两者名称近似，但作者、来源与内容均不同，不能合并引用。

官方 PDF 简介列出 AIDC 数字投手、千问用增 Agent、万有无界三个案例，以及环境与验证驱动、平台能力升级、提效度量、数字员工、组织配套五类挑战。第三部分包含 Harness、企业知识、MCP/Skill/CLI、Sandbox/Coding 环境、身份与权限、生产 Guardrail、可观测。

重点核对：

- PDF 第 21–24 页（正文印刷页 16–19）：批评仅按 PRD→方案→任务→编码→测试固化流程。主张 Agent 能自主获取验证信号、迭代推进；Workflow 继续承担调度、权限、状态、审计和高风险检查。Spec 要区分长期约束与可被验证修正的方案假设。
- PDF 第 25–27 页：平台需要可靠入口、明确资源对象和可推进任务的反馈。“能调用工具”不代表“知道该操作哪个资源”。MCP 本身不解决对象定位和完整研发上下文。
- PDF 第 28 页起：把 Session→Commit→Change→Workitem 串成归因链。分三层衡量：L1 使用与 AI 效能、L2 工程质量、L3 价值交付，防止只优化代码占比或 Token 消耗。
- 简介的“10x”是所期望的效能空间，不能当成阿里全组织已达成的结果。编码占研发时间 20%–30% 的表述明确是团队粗略统计，也不能泛化到所有团队。
- 第 21 页模型 benchmark 表自行注明“2026 年 7 月快照，各来源口径不一，仅供参考”。不拿它比较模型优劣，也不据它宣布企业编码问题已完全解决。
- PDF 第 6–8 页将“超级个体→数字员工→云上 Scrum”写成团队经历，列出中间产物难消化、岗位孤立、质量波动和人肉调度等失败点。其中广告 Agent 产品自身的“经验/手脚/头脑”架构，与用 Coding Agent 开发它的协作流程是两件事，不能混用。
- PDF 第 33 页区分进入现有组织的数字员工与独立 Agent 身份授权，两条路线并存；强调技术身份不能自动解决组织责任。
- PDF 第 34–35 页关于 AI 几乎无限记忆、没有沟通衰减、岗位合并、小团队天然优于大团队等，是组织演进观点。模型仍有上下文、成本、错误传播和协作损耗，不能据此直接推导组织结构。
- PDF 第 67 页作者明确说明：“它不是一份成熟的方法论，更谈不上标准答案——很多做法还在验证中，有些方向看得到趋势但尚未跑通。”这限定了整本手册的证据强度，也支持先补充资料再作设计决定。

另有 [第三方 HTML 解读版](https://kejun.github.io/ai-native-dev-handbook/)。它便于检索，但夹有解读，本文以官方 PDF 核对重点，不把第三方新增解释当成阿里原话。

## 腾讯：完整交付闭环的具体实现

2026 年的文章描述海外网络运营内部平台 Vibe Flowing，适用边界很明确：成熟 SDK、可复用框架、统一身份与权限、云开发容器构成前提，运营人员在这些基础能力上提出需求并验收。

值得保留的机制：

1. 简单需求对话澄清，复杂需求形成文档；需求→实现→确认提交有显式阶段边界。
2. Rules 与 Skills 分工、按场景加载。规范包括分层、DB 变更、验证命令，工具封装高频操作并留痕。
3. 开发环境自动准备、可预览，AI 能启动服务、查看日志、跑静态检查和浏览器验证。
4. AI 做完验证与推送后创建 MR，管理员审查合并；文中 AI 审批仍是正在引入的能力。
5. 评论 open/resolved/closed 与规格 draft/ready 是不同对象的状态；文件名前缀是此项目的轻量协作方案。
6. 能力地图帮助非开发者理解已有功能；组件化和 Storybook 降低 AI 探索与人工审查成本。

局限：3 分钟环境准备是该团队的实践报告，未见跨团队对照和分布统计。规则文本写明约束，并不证明每次遵守；关键限制仍需工具、权限和 CI 执行。“工具返回 Markdown 比 JSON 省 Token”、所有项目使用单仓等，均依赖具体场景，不能作为通用定律。

2025 年 CodeBuddy 文则更强调模板和文档驱动。其 5 万用户、编码时长下降 40%、AI 代码占比超过 43% 属文中自报，缺少足够统计方法；它们衡量的也不是完整需求交付周期。产品形态和路线图应按今天的产品文档再查。

## 字节：把团队流程与 Agent 内部循环区分开

洪定坤演讲的媒体报道给出：TRAE 团队半年代码 AI 产出超过 90%，人均需求吞吐提高 60%；900 次运行中功能正确率与可交付质量之间存在差距，引入 Harness 后改善。这些目前是**媒体转述**，没有读到完整原文、原始任务集、评分规则和实验配置，不能当成我们的量化承诺，也不能把 TRAE 团队数字推广到字节所有业务。

更可核查的材料是 Trae Agent 论文 v1：

- 研究范围是 SWE-bench Verified 仓库级 issue 修复；通过候选补丁生成、剪枝和选择探索解空间。
- 实验比较使用相同候选补丁池，涉及 Gemini 2.5 Pro、Claude 3.7 Sonnet、GPT-4.1；有消融与有效性讨论。
- 文中 75.20% Pass@1 与榜首明确属于 2025 年 7 月的快照，不能当作当前榜单结论。
- 最终提交一个补丁的 Pass@1 不等于内部只生成一次；候选搜索消耗也应计入成本。
- 开源 CLI 的工具、模型配置、Docker 模式与执行轨迹便于研究，但当前 README 展示的通用 CLI 不能直接视为论文所有实验模块的完整复现。
- issue benchmark 的测试通过不等于业务发布可用，不覆盖组织协作、生产约束与真实经济收益。

QCon 的张聪讲师介绍说明，Agent 内部从固定 Proposal+Plan 向自主 Loop 演进，同时专家经验依赖场景仍适合固定 Workflow。这支持将**内部执行策略**与**外部交付约束**分别讨论：内部允许按反馈重新规划，外部仍保留验收标准、权限、证据与责任边界。它没有证明团队层面不再需要 Spec。

## 美团：尤其适合补足存量系统与评审瓶颈

31 万行系统的官方实践覆盖从技术债梳理到规范制定，再到渐进式迁移。团队负责人先迁移两个复杂包并沉淀 SOP，其他成员随后推广执行。规范约束分层、业务域、仓储职责；技术债结合业务迭代逐步消化。

它提供了两项重要反例：

- AI 提速后 Code Review 成为瓶颈，需要 Pre-PR 自查和明确影响范围的 PR 说明；人工重点审查技术方案及业务语义。
- 全自动生成测试用例暴露出高危关联漏测、无价值用例和审查负担。最终由人确定范围与风险深度，AI 辅助扫描、分组、展开步骤和覆盖检查。

文章的“90% 以上 AI 编码”“10 个性能隐患”等是团队自报。31 万行是系统体量，不是宣称逐行重写 31 万行。没有专门申请重构排期也不等于重构没有工时。高阶或不同厂商模型互审是其策略，不能消除相关性错误，仍需测试与人工裁决。

美团的单测文章进一步按场景选择：简单功能先实现后验证、复杂逻辑 TDD、存量修改使用回归安全网。腾讯文章则不追求严格先写测试，强调避免弱断言。这不是谁对谁错，而是应同时评估需求能否事先表达成测试、已有测试质量与真实业务风险。

## 华为：提供高复杂系统的另一条路线

InfoQ 材料强调将成熟工程方法、模板、规范、检查表、历史缺陷和评审经验融入 AI；需求与架构先形成工程契约，后续按角色权限、代码检视、测试、安全检查与灰度发布推进，保留 Committer 决策。

它与腾讯轻量运营系统的适用范围不同，更接近复杂遗留系统的全流程质量治理。对于我们之前涉及的 BSP、底层并发与可靠性问题，这类工程纪律更值得参考；仍需补齐实际硬件、时序与运行态验证，不能只靠代码模型评审。

文章中的“确定性”“绝对可验证”“每一行都符合”等是强烈的目标或宣传措辞，未给出足以证明无遗漏的形式化与实验依据。其知识图谱段落自身也提示随模型能力提升可能不需要做那么多，不能由此推导必须先搭建完整知识图谱平台。

## 对此前讨论的修正与后续资料缺口

这些资料能共同支撑的判断：

- 评价 AI 原生研发应围绕需求到交付、质量和总成本。代码生成量适合观察使用情况，不足以证明产能改善。
- 工程环境、可执行验证、领域资产和团队共识，是反复出现的关键条件。
- 专业人员要保留业务语义、风险、架构和最终交付责任；非开发者参与仍需要专业底座。
- 多 Agent、知识图谱、完整平台不是统一前提。应分清单 Agent 执行闭环、跨角色评审和跨任务协作。
- 固定工作流与自主循环可以并存；任务约束、状态与证据不能简单等同于 Agent 的思考步骤。

仍需收集：

1. 字节演讲完整原文或官方实录，核对 900 次实验与吞吐统计方法。
2. 大厂在发布后故障、回滚、长期维护方面的量化材料，避免只收集开发阶段成功案例。
3. 阿里手册中的数字员工协作、身份权限与持久任务机制是否有可读代码或详细 API；概念说明不足以选择我们的任务引擎。
4. 百度内部团队的第一人称流程材料；当前官网和泛化评测文章不足以代替工程实战。
5. 针对 BSP / 内核 / 嵌入式的 AI 研发与实机验证材料。当前样本以 Web、运营系统、业务后端与通用仓库修复为主，存在领域迁移缺口。

### 新增材料带来的核对点

**阿里不是统一采用一种流程。** 跨境保险文章采用 OpenSpec、多模型分工和每阶段人工审查；淘特文章则明确谈到规格写作成本、工具不成熟、历史代码集成困难，并采用融合策略；2026 年集团手册强调环境与验证驱动。它们反映团队范围与时间变化，不应概括成“阿里已经统一证明 SDD 最优”或“阿里已经全面放弃 Workflow”。

跨境保险文章标题的“全流程”也不等于全程无人参与。其正文明确包含需求澄清、阶段暂停、人工 Review 与最终验证。多模型职责分工是该作者的经验配置，随模型版本变化需要再评估；没有充分对照数据证明它优于单模型方案。本文只读取外部配置示例，不应用其中的命令和约束。

**腾讯广告审核的两篇文章可以按时间对照。** 2025 年围绕技术方案生成代码，报告研发节约时长 30%+；2026 年将能力扩展到测试与部署。后一篇的“80% 效能提升”出现在目标描述中，不能当成已实现整体收益。正文明确当前测试用例由人工梳理结合 AI 辅助，尚不能端到端自动生成完整测试用例；六个试点不足以证明中心所有需求均可无人交付；治理框架尚在规划。值得记录其环境创建、操作步骤等具体变化，并继续核查统计方法。

**字节官方资料分布在多种载体。** 除洪定坤的大会分享，已有 Trae Agent 论文、QCon/AICon 的工程主题、TRAE 认知演进、veCLI 与 veRL 资源。团队工程经验、产品运行时与训练方法不是同一个层面，应分别建立阅读目录。
