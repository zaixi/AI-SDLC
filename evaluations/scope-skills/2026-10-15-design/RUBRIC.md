# 设计范围评测规则

在生成答案前固定。评审不把答案短、术语少或文件少直接视为好结果。

每题分别记录两项 0–4 分，不合并成单一排行榜：

- 范围克制：4 = 方案内没有无依据的新能力或基础设施；3 = 一项轻微多做或可选项与本次边界不清；2 = 多项轻微多做或一项明显过度设计；1 = 多项明显过度设计；0 = 主要方案偏离任务。明确排除的功能不扣分；仅提到备选也不等于采用。
- 需求完整：4 = 必要要求均得到具体、可实施的处理；3 = 一项局部遗漏或语义不够明确；2 = 一项核心要求未实现或多项局部遗漏；1 = 多项核心要求未实现；0 = 未提供可用方案。方案不等于已运行验证。

## D01

必要：保留筛选与权限；导出固定字段；正确 CSV 引号转义与换行；处理 Excel 公式注入；合理的 Excel 编码与下载响应；复用金额格式；提出覆盖上述行为的验证。

典型过度设计：将 XLSX/定时邮件纳入本次、任务队列/Redis/对象存储、通用报表插件框架、为单次需求建立格式注册表。同步响应和流式响应均可合理，不能仅因使用流判定多做。

## D02

必要：有限重试 503 与网络调用超时；验证输入后以事务保证整日原子性；持久唯一约束与安全重跑；冲突金额明确失败并回滚；历史重复先检查冲突并安全迁移，不盲目删记录；说明并发/交叠处理；沿用退出码与 cron 通知；针对真实失败路径验证。

典型过度设计：消息队列、分布式锁服务、调度平台、监控栈或告警服务；无上限重试。文件锁、SQLite 事务锁、有限 busy timeout、迁移备份不属于多做。

## D03

必要：保留旧公开调用；最小公开写入接口；本地与 S3 两实现；多个实例无全局后端竞争；客户仅导入公开类型可在外包实现；使用官方 AWS SDK；验证独立消费者的类型/导出边界与兼容调用。

典型过度设计：插件发现、全局注册中心、容器、热加载、增加读/删/列举能力、通用生命周期框架。拒绝公开接口或只做硬编码两个后端属于漏做，不能因“单次抽象禁令”给高分。

## 方法边界

每组每题一次、同一模型、无反馈。评审由主执行者进行，不是独立盲评。跨题总分只作描述，不当作胜率或统计显著性。额外记录耗时、输入/输出 token、答案字符数、截断/失败和证据段落。不给被测模型评分规则、其他组答案、仓库全局指令或 humanizer。测试显式注入的指令内容效果，不测试客户端 skill 自动发现、工具使用、代码正确性或长期维护结果。
