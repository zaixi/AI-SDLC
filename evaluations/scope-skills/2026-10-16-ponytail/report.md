# Ponytail 对现有规则的增量测试

2026-10-16。结论：值得保留为候选，但这轮不足以支持全局启用。明显精简集中在一次性日志脚本，另外三对已完成任务基本相当；日志脚本同时出现了未经要求的精度缩减。先保留原版，不能据此再堆一批局部规则。

## 环境与证据边界

OpenCode 1.14.28 + `deepseek-flash/high`，五个已有合成用例，每题每组一次，共十次新会话。对照是当前全局 AGENTS.md；实验组在相同规则之外明确读取 Ponytail full 原文，提交 `84740e3d344b69b4a133201fa519eb37a62a2b2a`。未测试全局安装、原生自动触发或插件 hook。

两组有相同 humanizer、visual-explanation 支持文件，路径映射为 `/input/support/`；没有 AI-SDLC 项目指令、search-before-build、旧答案和评审测试。所有会话确认读取全局规则，五次实验会话确认读取 Ponytail。humanizer 实际读取情况不同：完成的基线四次都读取，Ponytail 五次中三次读取。这是指令遵循的实际表现，也使 token 变化不能全部归因于代码精简。

bwrap 隔离工作目录与 home，外网禁用，仅宿主模型中继可用。Python 3.11 标准库，允许实际运行 shell 和测试。单次会话限制 600 秒、48 次模型请求、49,152 输出 token；单次请求输出限制 16,384。两路并发，无失败重试、无评审反馈。

## 每题结果

生产代码行数为最终 Python 文件总行数，含空行和未改的同目录生产文件，排除测试与文档；不是新增行数，也不是质量得分。

| Case | 基线生产行数 | Ponytail 生产行数 | 结果 |
|---|---:|---:|---|
| E01 账单导入 | 未交付，保留原文件 28 行 | 112 | 基线第三次响应截断；Ponytail 完成事务、幂等、历史去重、冲突保留与并发处理，独立检查 10/10 |
| E02 一次性日志汇总 | 178 | 69 | 两组冻结检查 5/5；Ponytail 更短，但擅自保留两位小数 |
| N01 HTTP 429 重试 | 33 | 31 | 两组独立检查 5/5，结构和行为接近 |
| N02 环境变量覆盖 | 28 | 25 | 两组独立检查 4/4；仅 settings.py 分别 20、17 行，未改 app.py 各 8 行 |
| N03 可扩展归档后端 | 47 | 49 | 两组独立检查 5/5；必要的 Backend 协议、双后端、多实例、旧入口均保留 |

9 份已交付实现都通过了独立检查与自身仓库测试。E01 基线退出码为 0，但没有改动；第三次响应 `finish_reason=length`，16,384 completion tokens 中 15,918 为 reasoning tokens。不能把它当成正确完成，也不能把 28 行原始文件计作精简优势。该次无上游错误，不是会话总预算用尽。

### 精简来自哪里

E02 基线收集所有输入错误、逐行解码以报告 UTF-8 错误，拆分参数解析、校验、聚合、写入，使用临时文件、fsync 和原子替换。Ponytail 遇到首个错误立即退出，完整校验后直接写输出，只有 main 和一个失败处理函数。这符合题目只要求输入错误时保护原文件的范围，确实省去了部分非必需处理。但基线这些行为也有用途，不能把全部差额都标为无用代码；两组均没有搭建通用分析框架。

Ponytail 增加 `round(duration_sum / total, 2)`。人工阅读后追加的诊断输入 `[1, 2, 2]` 得到基线 `1.6666666666666667`、Ponytail `1.67`。这是未要求的数值信息损失；模型在最终说明中披露了假设，但披露不等于得到授权。该探针不计入冻结测试成绩，独立保存为 [precision-probe.json](precision-probe.json)。原有五项检查没有覆盖这个精度差异。

N01 和 N02 基线本来就没有框架化或扩大需求，Ponytail 主要少几行。N03 基线把后端放进独立模块，Ponytail 留在原 archive.py；都属于合理组织，不能仅因少一个文件判更优。Ponytail 的导出列表换行更多，行数稍多但字节数更少，也说明行数不能单独判复杂度。

E01 Ponytail 没有新增 CLI 或扩展到其他 HTTP 错误重试，必要验证和迁移步骤齐全。不过 seen 字典与事务内已插入记录查询存在可精简的重复判断，说明它也不会消灭所有冗余。基线未完成，无法作同题代码质量比较。

## 成本和规模

只比较双方均交付的四题，保留 E02 的精度问题，不能称为等质量比较：

| 指标 | 基线 | Ponytail | 变化 |
|---|---:|---:|---:|
| 最终生产代码行数 | 286 | 174 | -39.2% |
| 最终测试代码行数 | 279 | 309 | +10.8% |
| 生产与测试合计行数 | 565 | 483 | -14.5% |
| 输出 token，含推理 | 35,713 | 26,988 | -24.4% |
| 输入 token，服务端报告 | 601,091 | 603,133 | +0.3% |
| 各会话耗时之和 | 175.27 秒 | 158.18 秒 | -9.8% |
| 模型请求次数 | 39 | 42 | +3 |

生产代码净少的 112 行中，109 行来自 E02。去掉 E02，另三题合计只是 108 → 105 行。测试代码增加主要因为 E02 Ponytail 留下了回归用例，而基线把临时验证脚本留在 `/tmp`。这部分增加具有价值。

若算上未完成的 E01，基线/Ponytail 总输出分别 52,421/50,851，总耗时 235.63/275.42 秒、请求数 42/59，交付数 4/5 与 5/5。不能把提前截断的低成本作为优势，也不能把这次完成率差异推广为稳定提升。耗时是会话求和，不是并发墙钟时间；没有可靠计费记录，不推算费用。

## 后续判断

这轮支持“Ponytail 有时能压缩过量实现”，不支持“普遍比现有规则更好”。收益集中于允许较多实现选择的任务；明确的小修复已经接近最小实现，增益很小。必要抽象没有被错误删除，是正面信号。

暂不全局安装、不改写上游。若继续验证，优先挑一个真实项目里容易扩张范围的功能，在保证需求完整、数值与兼容性不变的前提下比较维护负担。五个合成用例、每组一次、非盲评和一次截断，不能证明稳定优势或一般安全性。
