新同事先看区域和八步主链。值班工程师用后面三张失败表查作业状态，以及哪些单元不重跑。

## 区域与内部单元

四个区域，14 个内部单元，不合并。外部邮件服务不属于平台。部署方式未提供。

```tree
接入
  上传页 | 供用户提交原件
  接收 API | 保存原件并建立作业
  原件库 | 保存原始文件
处理
  作业表 | 保存作业状态
  调度器 | 找到待处理作业并派发 OCR
  OCR 工作者 | 识别原件并保存文本
  文本库 | 保存识别结果
检索
  索引工作者 | 读取文本并更新搜索索引
  搜索索引 | 保存可查询的索引
  查询 API | 读取搜索索引
  搜索页 | 供用户检索
运维
  状态页 | 供用户查看作业状态
  状态 API | 只读作业表
  通知器 | 找到已完成作业并调用外部邮件服务
平台外
  外部邮件服务 | 不属于平台。发送完成通知
```

## 成功主链

实线是调用、写入或通知。虚线是只读。每步只画本步的单元。步骤 6、7 不改变作业状态。

```flow TB
(上传页) -> [接收 API]: 1 提交原件
[接收 API] -> [(原件库)]: 2 先写入原件
[(原件库)] -> [(作业表)]: 2 写完后，接收 API 再建立待处理
group 步骤 1–2 接入: 上传页, 接收 API, 原件库, 作业表
```

第二段箭头只表示先后。建立作业的仍是接收 API，不是原件库。

```flow LR
[调度器] --> [(作业表)]: 3 读取待处理
[调度器] -> [(作业表)]: 3 先改为处理中
[调度器] -> [OCR 工作者]: 3 然后派发
group 步骤 3 处理: 调度器, 作业表, OCR 工作者
```

先读，再改状态，最后才派发。对作业表的读和写是两条边。

```flow TB
[OCR 工作者] --> [(原件库)]: 4 读取原件
[(原件库)] -> [(文本库)]: 4 识别后，OCR 写入文本
[(文本库)] -> [(作业表)]: 4 写完后，OCR 改为待索引
[(作业表)] -> [索引工作者]: 4 改完后，OCR 通知索引
group 步骤 4 处理到检索: OCR 工作者, 原件库, 文本库, 作业表, 索引工作者
```

这一链的动作都由 OCR 工作者完成。中间存储只标先后，不表示它们自己通知下一环。

```flow TB
[索引工作者] --> [(文本库)]: 5 读取文本
[(文本库)] -> [(搜索索引)]: 5 读完后，索引工作者写入
[(搜索索引)] -> [(作业表)]: 5 写入成功后，改为已完成
group 步骤 5 检索: 索引工作者, 文本库, 搜索索引, 作业表
```

改为已完成的是索引工作者，而且只在索引写入成功之后。

```flow LR
(搜索页) -> [查询 API]: 6 调用
[查询 API] --> [(搜索索引)]: 6 只读
(状态页) -> [状态 API]: 7 调用
[状态 API] --> [(作业表)]: 7 只读
group 步骤 6 检索: 搜索页, 查询 API, 搜索索引
group 步骤 7 运维: 状态页, 状态 API, 作业表
```

```flow LR
[通知器] --> [(作业表)]: 8 读取已完成
[通知器] -> (外部邮件服务): 8 调用发送
```

外部邮件服务不属于平台，所以步骤 8 不画运维组框。

## OCR 失败影响哪里

OCR 工作者把作业表改为失败。再次处理需要人工重新排队。入口未确定，所以不画排队动作。

| 单元 | 这条失败下 |
|---|---|
| 作业表 | 状态改为失败 |
| 状态页 / 状态 API | ok 仍只读作业表，可见失败 |
| 索引工作者 | no 作业不进入待索引，OCR 不通知它 |
| 搜索索引 | no 本次作业不更新 |
| 搜索页 / 查询 API | warn 仍只读已有索引，看不到本次作业 |
| 通知器 | no 只找已完成作业，不发完成通知 |
| 外部邮件服务 | no 收不到这次完成通知 |
| 原件库 | warn 原文未写失败时原件是否保留 |

调度器只找待处理作业。失败作业不会被它再次派发，除非人工重新排队。谁来排队尚未确定。
