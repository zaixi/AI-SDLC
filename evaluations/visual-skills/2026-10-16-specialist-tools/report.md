# 复杂图工具实测：visual-explanation、Archify、Fireworks

2026-10-16。两题各三组、每组一次，已完成六次尝试，未重跑。结论：Archify 的复杂总览与 Fireworks 的静态插图有值得继续验证的表现，但本轮没有证明它们能稳定降低生成成本，也不足以据此替换或新增默认依赖。保持现有入口不变。

## 完成情况与成本

OpenCode + deepseek-flash/high，文本输入，模型可执行工具和浏览器 DOM 检查，不能看图片。每会话 600 秒、48 次请求、49,152 输出 token；每响应上限 16,384。全部运行的最后一次响应为 length：五次达到总输出上限，V02 visual-explanation 在写文件前达到单次上限。进程退出码均为 0，不能据此视为成功。

|---|---|---|---:|---:|---:|---:|
| V01 平台全貌与失败影响 | visual-explanation | 六图、多表的离线 HTML；无完成交付回复 | 215.55 | 23 | 1,214,629 | 49,152 |

## V01：Archify 的成品更紧凑，但流程仍然昂贵

### Archify

实际画面是一张按接入、处理、检索、运维划分的总览，下方四张卡片分别说明职责、成功顺序、失败规则和不受影响部分。14 个内部单元和外部邮件服务保留，原题的 OCR、索引、邮件三类失败状态与重试边界也保留。单张图比六视图长页面更容易先建立整体认识；失败细节主要依靠卡片，不能说它把每条失败路径都画成了图。

首轮被 showcase 的 label-route-clearance、连接间距和 label-gap 检查拦住。之后修复，最终 validate、deliver、check、browser-check 全通过；评审阶段也实际打开了 HTML。花了 49,152 输出 token、约 339 秒后没有剩余预算完成最终回复。该次 reasoning tokens 为 43,699，不能把全部开销简单解释为生成 HTML 很长。

### visual-explanation

模型实际读取三个可选 skill，最后使用本地 Mermaid 运行时生成 HTML，而非使用 am 组件。成功链被拆成时序图，三类失败各有图，另有单元表和影响矩阵，资料覆盖较细。

问题有两个。首先，总览原始宽约 2,801px，被缩进页面后节点和边标签过小。模型发现这个问题，继续尝试布局，最终耗尽预算，交付文件仍保留过小的总览。其次，它将“OCR 失败”进一步解释成“文本库本次无写入”，将“索引失败”解释成“索引未更新、该文档不可检索”。材料未给出失败发生时点与写入原子性，这些后果不一定成立。部分位置标为推断，但另一些图节点直接断言；不能以信息更多作为更准确的证据。

页面高度约 6,942px，长本身不是错误，但在本题目标下，反复呈现单元、步骤和失败影响增加了阅读量。Archify 的总览配卡片更紧凑；这只是本次人工判断，未进行真人阅读实验。

### Fireworks

留下的总览 SVG 结构可读，14 个内部单元和外部邮件服务均在，区域分组清楚。实际流程先读取脚本与生成器、运行试图，再反复调整长连线。截止时没有 HTML、失败影响细节和完整交付，因此不能用这张较整洁的局部图判整题优胜。

## V02：Fireworks 的 SVG 最适合本题的静态文档用途

### Fireworks

SVG 横向依次排列东站、中心、西站；各站独立采集器、网关和缓冲库，中心汇总服务、归档库，总共八个实例齐全。上报与补传使用相反箭头、不同颜色及实虚线；缓冲读写分开表示；传输协议、认证、队列均标为未定。成品尺寸约 1,360×580，适合嵌入文档。本次没有发现影响理解的关键语义遗漏。

但它为处理补传箭头的折弯数、短线段和标签障碍多次调试生成器。中间 render 报出 EDGE_BEND_BUDGET 和 EDGE_MICRO_SEGMENT，模型还检查了内部路由实现；最后得到 showcase 通过的 SVG，却在 PNG 导出前耗尽预算。可读的 SVG 是正面证据，完整交付失败则说明这套流程在本环境里仍不够省事。不能断言所有几何检查都多余，也不能说它们的收益抵得过这次成本。

### Archify

留下的 HTML 同样保留八个实例、上下行关系和待定事项，自身检查通过，实际浏览器可打开。图采用上下两站、右侧中心的布局，交互界面和说明卡片适合独立浏览，但没有导出题目要求的 SVG/PNG，因而没有可直接比较的文档导出成品。

卡片另写了“两站之间无直连”；原题只列出已知关系，没有确认额外关系不存在。较准确的表达应限定为图中展示的关系，而非推断实际网络拓扑。站内箭头标“读写”，与 Fireworks 分开的双向缓冲箭头相比，方向表达较概括。

### visual-explanation

模型选择 diagram-design，读取多份引用、模板和导出脚本。最后一次响应的 16,384 token 全部为推理，直接截断，没有文件。该题说明本次模型、调用方式与上限组合未完成任务，不能证明 visual-explanation 原则上不会画这张图。

## 是否接入现有入口

本轮不改 visual-explanation、不全局安装候选。

- Archify 保留为复杂关系 HTML 图的候选。它这次最有价值的是紧凑结构与现成查看器，不是节省 token 已得到证明。
- Fireworks 保留为文档 SVG 插图的候选。双站图的空间组织和双向关系表达较好，但完整导出效率尚未得到证明。
- 不能从这些结果推断可以替换 answer-me-with-html：本轮没有专门比较图、表、代码与文字混排的组件场景，现有入口也没有实际调用 am。
- 暂不针对失败新增低等级几何规则。若继续，应先确认模型/推理模式与合理预算能稳定完成，再看同等完整交付下的含义、易读性与成本。不要沿用这次预算截断的数据宣称稳定排名。

## 环境与评测限制

1. 每题每组一次，非盲评，仅两题；两个候选的新版本和现有入口的可选依赖版本不同，来源均固定。这是完整方案比较，不是提示词的纯消融。
2. 五次达到总输出上限，另一次达到单次响应上限。触顶的是“含推理的 completion token”，并非最终文件的字数；总量不能直接说明文件臃肿。
3. 模型不能看图片，仅有文本与浏览器工具输出。生成结束后主 Agent 才看图，未把反馈发回，因此不是带视觉自纠错的最佳能力测试。
4. Fireworks 未安装 GIF 依赖，未请求 GIF；静态三个格式的样例预先通过。Archify 官方样例 finalize 也预先通过。下载排障未计入生成。
5. 当前 visual-explanation 整包包含维护用 AGENTS.md 和 README，模型看到了维护说明；其中指向历史评测的相对路径不可达，未暴露旧答案或评审标准，但仍是不理想的额外上下文。下一轮应事先定义仅生成所需文件的 allowlist。本轮保留原始记录，不通过事后删除文件伪装干净环境。
6. 生成期间可见的是各组自己的文件和依赖，没有其他组产物、主仓库或全局规则。模型鉴权在宿主中继，外网禁用。
7. 全部五份主要可视产物已在浏览器实际渲染并人工查看；未测试所有查看器交互、手机适配或动画导出。审阅截图不补算模型未完成的 PNG。
