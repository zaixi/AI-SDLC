# 更有区分度的两题：选图、拆图、C4 与真实渲染

2026-10-09。三组各两份回答，共六个新容器与临时 CLI 会话。**[直接看实际图片与原始回答](comparison.md)**。14 个图块通过 Mermaid 12.1.0 解析，也全部成功生成 SVG 和 PNG；渲染成功不等于图已经好读。

## 题目为什么不同

第一题混合组件协作、发布状态、批次结果去重和角色约束，要求模型自行选择并组织视图，不指定图种或图数。材料没有确认权限校验的具体实现位置，不能为图完整而补成现状。

第二题要求 C4 体系的业务与工程两个层级，但不强制使用 Mermaid 的 C4 专用语法。包含三个组织、十二个内部运行单元、三套独立数据库、十九条容器级关系，以及外部订单、交付、付款和回调路径。需要同时保留边界与通信方向，不展开外部系统内部结构。

题目和核对要求在生成前写入源目录；原文见 [prompts.json](inputs/prompts.json) 和 [rubric.json](rubric.json)。这些仍是合成案例，不代表真实项目设计已被验证。

## 输出区别

| 条件 | 第一题的组织方式 | 第二题的组织方式 | 本轮可见的问题 |
|---|---|---|---|
| show-me | 协作流程图 + 状态图 + 权限表；1330 字符 | 两张 flowchart 表达 C4 两层；2240 字符 | 文字建议 API 校验位置，超出已确认内容；C4 上下文标签拥挤，容器图仍有交叉线 |
| mermaid-diagrams | 协作图 + 状态流程图 + 批次时序图；1894 字符 | C4Context + C4Container；2990 字符 | 图中将 API 权限校验画成现状；专用 C4 图布局存在明显问题 |
| visual-v041 | 协作图 + 状态图 + 批次时序图 + 权限表；1899 字符 | C4Context + C4Container；2905 字符 | 本次明确未提供权限校验实现位置；仍继承专用 C4 图布局问题 |

字符数包含源码和正文，不是质量分。三组都覆盖了关键状态、角色和通信要求，没有因为多画一张图就自动得分。

第一题，show-me 的批次去重放在状态图批注中，整体更短；另外两组另画时序图，使批次条件和重复结果分支更显式，但增加阅读长度。show-me 自环没有明确写“仍有下一批”，完成条件另有转换；另外两组在标签中区分下一批与全部完成。权限校验位置方面，show-me 用“应”给出建议，Mermaid 组直接加在 API 节点上，0.4.1 明确材料未指定实现位置。建议与未确认的现状不能混同，也不把这些问题夸大成已证实的运行故障。

第二题，参考指引确实影响了图种选择：show-me 采用普通 flowchart，另外两组采用专用 C4 语法。普通 flowchart 只要保持 C4 层级与边界，也符合本题要求；不能因为它没写 C4Container 就判错。

## 实际画面揭示的问题

两份专用 C4 上下文图的相反方向关系共用直线，消息标签重叠。两份容器图把十二个运行单元排成很长的单列，长连线穿过中间节点，关系标签与节点文字相互叠压。源关系存在、语法正确，但读者很难沿图追踪交付与付款路径。需要调整布局或视图组织。

show-me 的 C4 容器图在本次渲染中更紧凑，关系较容易追踪，仍有交叉线；它的上下文图也有重叠标签，不能称为完整的可读性通过。第一题的协作、状态和时序视图总体可辨；更多细节是否值得多一张图，仍需要用户按用途判断。

PNG 最长边统一限制为 1600 像素，长图在预览中会缩小；SVG 可以放大。字号大小会受预览比例影响，节点穿线和标签重叠在 SVG 中仍可观察。结论针对本次源码与 Mermaid 12.1.0 渲染，不推断所有 C4 渲染器都如此。

内容及布局核对由主 Agent 完成，来源标签可见，**不是独立盲评或读者研究**。见 [content-review.json](content-review.json)。六份回答、14 张 PNG 和 14 张 SVG 全部保留；没有手工改图后替换原结果。

## 对几个 Skill 的判断

这次题目能够拉开表达选择和忠实程度：show-me 仍能自行拆视图，额外 Mermaid 参考促使模型使用专用 C4 语法，0.4.1 在这份发布题中更谨慎地保留了未提供的信息。但专用语法没有自动带来更好的实际布局。

因此目前应把三件事分开看：**能选择和组织视图、能写对语法、能交付好读的实际图**。这轮后两组在 C4 语法选择上更具体，布局仍需复核；show-me 的模型基础能力足够强，也有越界建议和布局缺陷。每题每组只有一个样本，不能给出普遍胜负结论。

这些结果支持继续检查真实画面，尚不足以证明所有 Mermaid 场景都必须加载参考，或参考没有价值。本轮没有修改 Skill，也没有测试“自动加载”机制。

## 独立性与输入边界

沿用 [上一轮的容器输入方式](../2026-10-09-container-retest/README.md)：每份独立容器、`--no-daemon --ephemeral --ignore-user-config`，新主目录，只读本组输入，没有仓库、其他组或旧答案挂载，没有 Docker socket。仅共享只读的登录认证卷，不共享会话历史。官方 Codex CLI 0.162.0 使用同一默认配置；JSON 事件未提供实际模型标识，不声称与历史 Agent 测试匹配模型。

由于模型本地文件工具在此环境受限，Skill 原文和相关参考直接注入输入。第一题提供时序图、流程图参考，第二题提供 C4、高级特性参考；show-me 组不提供这些参考。这样比较的是指引文本的表达效果，不是原生发现、调用或参考选择。六份 CLI 记录只有回答完成项，未出现工具调用完成项。

本轮统一采用文本交付，没有测试 show-me 的 HTML 文件与打开分支，也没有把渲染结果回传给生成器改稿。它是六份首次回答的比较，不是完整工具能力或迭代交付能力的比较。

完整 [模型输入](model-inputs/)、[输入哈希](input-manifest.json)、[运行记录](runs.json)、[指标](metrics.json)、[协议](protocol.json)与 [CLI 记录](traces/)保留。模型调用使用网络代理，文件隔离不等于网络出口隔离。

## 渲染环境与失败记录

渲染在单独 Docker 容器内进行，不挂载生成器的认证卷。网络关闭、普通用户、capabilities 全部移除、`no-new-privileges`、只读根文件系统与输入，仅输出目录和临时目录可写。Chromium 使用与上游 CLI 容器相同的 Puppeteer 无内部沙箱配置，由外层 Docker 限制文件和网络访问；没有放宽生成器的 CLI 沙箱。

最初上游多层镜像在 Docker VFS 驱动下耗尽根磁盘；通过标准 Docker 接口清理本任务未使用镜像后恢复。暂时清空派生输入的方案被自动审批拒绝，未执行，仓库输入和原始回答未改。该失败见 [render-attempt-01.json](render-attempt-01.json)。第二次使用过时的 `-w` 参数，CLI 12.0.0 返回 unknown option；见 [render-attempt-02.json](render-attempt-02.json)。这些是环境/驱动问题，不计作 Skill 语法错误。

修正后使用单个依赖安装层的 Chromium 镜像、Noto CJK 字体和 npm Mermaid CLI 12.0.0，Mermaid 实际版本为 12.1.0。图片均从原回答提取的源码生成，最终 [render-results.json](render-results.json) 记录 14/14 SVG、14/14 PNG 成功；[syntax-results.json](syntax-results.json) 单独记录解析。

可复核脚本和依赖锁文件位于 [scripts](scripts/)。渲染驱动保留本次实际路径，工具目录可按锁文件使用 `npm ci --ignore-scripts` 重建，镜像由 render.Dockerfile 构建；图片失败记录与原始生成记录均未静默替换。不要再次拉取本轮已导致满盘的多层镜像作为默认方案。
