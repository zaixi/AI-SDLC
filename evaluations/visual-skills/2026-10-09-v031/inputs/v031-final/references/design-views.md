# 工程视图与细节深度

覆盖需求、理解、设计、实现、调试、验证、评审和交接。按当前问题选择图，不要求每个任务画全套。最小而充分意味着：足以解释或评审当前决定，而不是图越少、文字越少越好。

## 按工程问题选择视图

| 场景 | 要让人看懂的内容 | 可用视图 |
|---|---|---|
| 需求澄清 | 参与者、目标、范围与验收场景 | 业务流程、场景时序、范围边界图 |
| 系统理解 | 职责、依赖、所有权与关键行为 | 分层总览、调用树、局部时序或数据流 |
| 方案选择 | 候选方案差异、约束与取舍 | 同层次方案对比、决策路径图 |
| 任务拆分 | 可交付结果和真实阻塞依赖 | 任务依赖图；执行顺序不自动代表依赖 |
| 实现讨论 | 逻辑、接口、边界与改动 | 伪代码、调用树、局部图、diff |
| 调试与故障分析 | 复现时序、观测、候选原因与验证步骤 | 时序、事件时间线、故障路径或假设验证图；假设与证实原因分开 |
| 测试与验证 | 行为、条件、异常与验证覆盖 | 状态/流程图及覆盖标记；测试通过不代表全部状态已证明 |
| 变更评审 | 前后变化、影响范围与约束风险 | 前后图、diff、影响关系图 |
| 交接与复盘 | 当前进展、未决项、依据与下一步 | 任务状态或调查路径图，引用已有设计记录 |
| 发布与运行讨论 | 执行步骤、依赖、观测与回退条件 | 发布流程、运行拓扑、故障恢复图；绘图不授权实际部署 |

单张概览无法承载正确性所需的细节时，增加局部视图。先决定读者要理解什么，再决定抽象层次、图种和表达格式；不把所有问题都变成架构报告。

## 图要承载判断，而不只是目录

先确定本次要解释的问题：当前如何运行、哪里存在风险、哪个取舍需要比较，或下一步如何解除未知。选择与此问题匹配的视图；模块总览不是所有问题的默认答案。

- 只知道职责、不知道调用关系时，职责分组可以帮助定位，但不能代替评审结论。可在图旁或图内标出关键风险、要查的现有契约、需要的证据；仍不编造模块连线。
- 缺现有资料时，核实与验证路径图可能比运行架构图更有用；明确它是工作建议，不是系统执行流程。查明现有机制后，缺正确性证据则验证，证据充分则复用结论；确认机制不足或选择未定时再作决策。
- 已有明确关系时，优先展示真实结构/行为，把风险或测试缺口标在对应位置，避免另建一张重复的流程图。
- 只看图及紧邻批注，应能识别本次核心关系、条件或下一步。不能理解时改视图或补信息；不为追求图独立而把长文全部塞进节点。
- 正文补充理由、依据和不适合画图的细节，不逐行复述图。来源和渲染状态用一处简短说明即可。

职责不自动证明模块之间有调用、关联或依赖。现有关系有待查明时，先标待核实；影响图的边只表达评审关注。未知项按 [规则](uncertainty.md)分类，避免把一组查询任务画成一组人的设计决策。

## 设计示例：看懂责任、边界和取舍

优先呈现系统与外部参与者、主要模块职责、数据所有权、依赖方向，以及影响设计的关键约束。边标明调用、事件或读写语义。

设计替代方案用同一层次的对比视图，突出不同的边界与代价。把“为什么这样划分”关联到决策原文；架构图本身不能替代取舍依据。

C4 的上下文/容器/组件分层可作为组织方法。只有渲染环境支持时才使用 Mermaid 的 C4 语法；否则使用分组 flowchart 或 SVG，照样表达这些层次。

## 行为与契约细节：适用于设计、实现、调试和验证

| 问题 | 推荐表达 | 需要覆盖的语义 |
|---|---|---|
| 接口与模块协作 | 接口关系图＋必要的契约表 | 输入输出、所有权、调用前提、失败语义；不必枚举所有函数 |
| 请求、回调、超时与并发 | sequenceDiagram | 同步/异步、必要的并行和分支、取消/失败、资源生命周期；顺序箭头不自动证明互斥或原子性 |
| 对象生命周期 | stateDiagram-v2 | 状态、事件、守卫、终态及禁止的转移；条件标签不自动证明已实现 |
| 处理流程与异常分支 | flowchart | 分支条件、终止条件、失败后的动作；不是所有异常都需要状态图 |
| 数据读写与信任边界 | 分组 flowchart | 来源、转换、存储、写入权限、缓存与跨边界校验 |
| 领域对象与责任 | classDiagram 或关系图 | 概念关系和责任，不把领域模型画成所有实现类的清单 |
| 数据表关系 | erDiagram | 标识、关联和基数；事务、一致性和迁移另用时序/流程表达 |
| 改动与兼容影响 | 同层次前后图或 diff | 变化点、受影响的契约、约束及验证缺口 |

根据需要，将锁范围、时延预算、重试策略、幂等前提、安全约束等标在相关交互或边界旁。数值与保证需有来源；不知道则标待核实，不编造。

## 总览与局部图

用总览提供定位，再展开决定正确性的局部行为。两层沿用同一套术语；局部图注明对应总览的哪个模块/交互。

技术细节只保留与设计判断相关的部分。真实代码结构按需读取；设计记录保留难从代码恢复的接口意图、约束、前提和理由。

## 委托 Mermaid 能力的输入

提供当前问题、选定层次、参与者及关系、约束、事实/目标/假设状态、来源和输出环境。只有能力确实可用且允许调用时才委托。拿回图后核对语义和遗漏，不以语法通过代替设计评审。

具体示例见 [diagram-patterns.md](diagram-patterns.md)。示例仅用于表达教学，不作为真实项目事实。
