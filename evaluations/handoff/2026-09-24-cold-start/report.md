## 一、评估设计

按 `METHOD.md:175` 的要求，并采纳 Superpowers 的实践教训——**用真实压力场景，不用问答测验**（其作者记录的早期失败模式正是 "gameshow-style quizzing"）。

| 设计项 | 做法 |
| --- | --- |
| 执行者 | 全新 agent，不继承任何会话上下文 |
| 可读范围 | 仅 ai-native-workflow 仓库目录，含 git 历史（`log`/`show`/`diff` 允许——`METHOD.md:140` 明确"缺少历史理由时可调查版本历史"） |
| 禁止 | 读取任何 `~/.codex/`、`~/.claude/`、`~/.agents/` 下的会话或记忆文件；禁止联网；禁止修改文件 |
| 任务形式 | 三个**真实维护请求**（"这两条边能合并吗""我该从零写吗""我想改成更严格的规则"），不是知识问答 |
| 判据 | 事先确定：结论是否正确、依据是否具体到文件/commit、是否如实区分「有明确依据／需要推断／找不到」 |
| 反编造要求 | 明确告知"诚实报告找不到比给出看似合理的推测更有价值" |

三个请求各自针对一类知识：**设计意图的区分**（为何拆两条边）、**被移除产物的历史**（kernel 原型）、**已否决方案的理由**（高影响事项是否一律单独批准）。

## 二、结果

### 请求一：能否合并 README 流程图中 C 的两条边

**结论：正确拒绝。性质：有明确依据。**

它定位到 `METHOD.md:14-19` 的权威流程图，发现两条边在原图中指向**不同节点**——`方向不符：纠正理解` 指向 B（重新调查），`方向成立：必要细化` 指向 C（在已有方案上细化）——并用 `overview.html:25` 与 `METHOD.md:61-67` 的表格交叉佐证，判定这是方法刻意区分的两条路径。

**意外发现（评估设计之外的收获）：** 它指出 `README.md:9-19` 在 `416cbff` 改版中把 4 节点压缩为 3 节点，导致**两条边现在都指向 B**——简化图丢失了原图的语义区分。这是一个此前未被任何一方发现的真实缺陷，由接力评估暴露。

### 请求二：工具实现应否从零开始

**结论：部分成功。**

- **"有过什么"——有明确依据。** 完整还原了 `2c3eaed` 中的 `kernel/` 原型：`SPEC.md` 的要求映射表、`check_assets.py`（444 行，即所问的"检查器"）、`verified_at` 绑定 commit 做漂移检测、`kind`/`authority` 区分事实与决定，并指出可用 `git show 2c3eaed:kernel/SPEC.md` 取回作为起点。
- **"为什么被移除"——找不到。** 它检索了 `edd43ab`/`2531f0d`/`c46252b` 的提交信息、`design-history-v0.5.md` 全文（grep `kernel` 无命中）、两份评审全文、`METHOD.md` 全文，确认三处材料都只记录"删除是经用户确认的决定"，**无一处说明决定的理由**。

它明确拒绝杜撰理由：**"不应替用户杜撰理由（比如'设计不成熟'之类），也不该假装从零开始而忽略这份已经具体实现过检查器和证据绑定字段的原型。"**

### 请求三：改为"高影响事项一律单独批准"

**结论：正确拒绝。性质：有明确依据。**

它在 `review-v0.8-by-claude.md:41-53` 找到该方案曾被逐字提出、否决及否决理由，并正确建议：不应把它当作未曾考虑过的新点子直接改 `METHOD.md`，而应先让用户知道这段历史，由用户决定是否推翻当初的否决。

## 三、判定

按 `METHOD.md:177` 的通过依据逐条核对：

| 依据 | 结果 |
| --- | --- |
| 关键保证是否保持 | ✅ 三项请求都可能破坏既有设计，全部被正确识别并拒绝 |
| 受影响行为的判断是否充分 | ✅ 依据具体到文件、行号与 commit，且交叉印证 |
| 必要知识是否同步 | ⚠️ 两项充分，一项（kernel 移除理由）缺失 |
| 是否靠原作者补充隐藏背景 | ✅ 全程无补充，隔离条件未被违反 |
| 有无无依据推断 | ✅ **零编造**，缺口如实标注并列出搜索范围 |

**判定：通过，附一个明确的知识覆盖缺口。**

`METHOD.md:177` 规定"资料缺失导致无法完成应记录为知识覆盖缺口，不能把所有失败归咎于接手者"——本次的缺口归因于资料，不归因于接手者。

## 五、一个反直觉的发现

评估设计者（Claude）事先的预判是：**请求一会失败**——因为解释"为何拆成两条边"的 `review-v0.6/v0.7` 评审文件已被移除，理由应当随之丢失。

**预判错了。** 接手者没有去找历史理由，而是直接从 `METHOD.md` 的图与表格中读出了**设计本身的区分**——规则已经体现在当前文档的结构里，不需要回溯任何历史。

反之，`kernel/` 移除的理由之所以找不到，正因为它**只存在于一次决定中，从未进入任何当前文档**。

由此得出一条可写入方法的结论：

> **让约束体现在当前文档的结构中，比把理由留在历史记录里更可靠。** 历史记录是补充手段，不是主要载体——这与 `METHOD.md:122`"能执行的约束尽量进入类型、契约、测试和检查"同向，但把适用范围从代码扩展到了文档结构本身。

## 六、局限

- **样本 n=1**，单一任务类型（文档型项目的维护判断），**不能外推到代码项目的接手能力**。
- 三个请求均由评估设计者选定，可能偏向已知的知识分布；未做随机抽样。
- 执行者是单一模型的单次运行，未做多次重复或跨模型对照。
- 本次评估**只测了"知识能否支持接手"这一项**，未涉及 `METHOD.md:166` 评价表中的其余三项（理解成本、自主执行收益、质量保持）。
- 隔离条件靠 prompt 约束保证，未做技术强制；执行者报告的搜索范围与本评估的记录一致，但无独立验证。
