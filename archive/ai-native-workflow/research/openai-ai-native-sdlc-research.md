# OpenAI AI-native SDLC / 软件工程研究

研究日期：2026-09-21  
范围：仅 OpenAI 官方网站、OpenAI Developers、OpenAI CDN；重点关注 AI-native engineering、SDLC、长任务、自主执行、质量保障、评审、文档和安全。  
用途：为 ai-native-workflow 仓库 `README.md` 的通用软件工程方法提供一手依据。这里的文章混合了团队实践、产品/客户案例和开发指南，不能把它们拼成一条强制流程。

## 结论先行

OpenAI 的材料共同指向几个方法判断：

1. **工作的单位从“写一段代码”转向“委托一个有边界、可验证的结果”。** 代理可以覆盖调查、设计、实现、测试、评审、文档和运维，但人仍需承担目标、关键取舍、风险接受和最终结果责任。
2. **长期自治的关键不是一条更长的提示词，而是可观察、可恢复的执行环境。** 代理需要真实代码/数据/日志/测试反馈，外部化的计划和状态，以及能在中途修正方向的机制。
3. **先做高信息量的整体判断，再逐步增加承诺。** 设计图、行为示例、可运行原型和小实验用于尽早暴露错误方向；实现细节不需要在编码前全部固定。
4. **测试不是最后一关，而是代理工作的主要反馈通道。** 需求、行为、结构、质量和运行层都要有对应证据；测试本身也必须审查，避免弱断言、虚假覆盖和只为通过而编码。
5. **质量保障需要“自动检查 + 独立代理检查 + 人的高风险判断”分层。** AI 评审适合扩大覆盖和发现跨文件/跨服务风险，但不能把代理的通过声明当作最终证明。
6. **自治水平应由环境成熟度和风险决定，不是统一的组织政策。** OpenAI 的 agent-first 实验能让代理端到端完成并合并，但文章明确说这是强依赖特定仓库、边界、工具和验证投资的结果；团队指南则继续要求工程师负责最终评审/合并。

### 1. Building an AI-native engineering team

- URL：<https://cdn.openai.com/business-guides-and-resources/building-an-ai-native-engineering-team.pdf>
- 日期：PDF 页面未给出明确发布日期；按内容使用上下文记录为 OpenAI 团队指南。
- 证据性质：面向工程领导者的实践指南，结合 OpenAI 经验和客户案例，不是规范或可复现实验。
- 关键机制：
  - 以 SDLC 的 Plan、Design、Build、Test、Review、Document、Deploy & maintain 说明代理可以承担的工作。
  - 使用 Delegate / Review / Own 分工：代理处理第一稿和机械工作；工程师检查准确性、完整性和系统影响；人保留战略方向、架构、最终评审、生产责任及高风险判断。
  - 建议把测试尽早写出，并可让独立会话生成测试，检查测试是否真实可运行、是否存在 stub/shortcut。
  - AI review 应面向高严重度缺陷、跨文件和运行行为，避免低信噪比评论；用真实 PR/评论建立评估集。
  - 代理可生成 Mermaid 等文档和发布摘要；人负责文档结构、关键 WHY、对外或安全关键内容。
  - 运行阶段把日志、部署、代码历史置于同一调查上下文，代理做初步诊断，人验证根因和修复。
- 对通用方法的启示：生命周期活动可以由 agent 贯穿执行，但职责不等于阶段审批；验收标准、测试意图、架构和风险责任必须在委托时明确。
- 局限：
  - Delegate/Review/Own 是责任建议，不是每个项目都要经历的固定门禁。
  - “把测试拆到独立会话”“先写 PLAN.md”等是有效实践，不是普适的文件结构要求。
  - 客户案例和 OpenAI 内部经验可能依赖 Codex、MCP 和组织能力，不能直接外推产能数字。

### 2. Harness engineering: leveraging Codex in an agent-first world

- URL：<https://openai.com/index/harness-engineering/>
- 日期：2026-02-11。
- 证据性质：OpenAI 内部五个月 agent-first 产品实验的工程复盘；不是通用标准。
- 关键机制：
  - 工程师的工作从手写代码转向设计环境、表达意图、提供反馈回路。
  - 仓库知识作为 system of record；短的 `AGENTS.md` 只是目录，深层文档、计划、架构、质量、可靠性和安全资料结构化放在仓库中。
  - 用 progressive disclosure 让 agent 先读小而稳定的入口，再按需深入；lint/CI 检查知识库新鲜度、交叉链接和结构，定期 doc-gardening。
  - 通过架构边界、不变量、结构测试和自定义 lint 机械约束 agent；中心强制边界，局部实现保持自由。
  - 代码、测试、CI、文档、评审回复、评估和运维定义都可由 agent 生成；人负责优先级、验收结果和缺失工具/规则的补充。
  - 反馈和用户缺陷反向写入规则或工具，防止“AI slop”持续积累。
  - 代理达到端到端自主，需要真实验证、恢复、反馈处理和权限边界的组合。
- 对通用方法的启示：把知识、计划、决策、证据和约束变成版本化、可导航、可机械检查的工程资产；“文档可读”还不够，必须“能被代理查找并用于验证”。
- 局限：
  - 固定的 Types → Config → Repo → Service → Runtime → UI 分层是该仓库选择，不应复制成通用架构。
  - 最小阻塞合并、代理自合并依赖高吞吐和低成本纠错；低吞吐或高风险系统不应照搬。
  - 文中承认端到端能力严重依赖特定仓库和工具投资，不能视为当前 agent 普遍能力。

### 3. Run long horizon tasks with Codex

- URL：<https://developers.openai.com/blog/run-long-horizon-tasks-with-codex>
- 日期：2026-02-23。
- 证据性质：约 25 小时、约 13M tokens、约 30K 行代码的单次设计工具实验；作者明确说明不是生产发布。
- 关键机制：
  - 长任务循环：Plan → edit → run tests/build/lint → observe → repair → update docs/status → repeat。
  - 真实错误、diff、日志是反馈；仓库、文件、工作树和输出是外部化状态；中途 steering 可以修正方向而不重置进度。
  - 用持久化的 Prompt/spec、Plan、Implement/runbook、Documentation/status 保存 goals/non-goals、硬约束、deliverables、每个里程碑的验收命令、决策记录、已知问题和恢复入口。
  - 每个里程碑失败先修复再前进；限制 diff 范围；不要把“做出令人印象深刻的东西”误当成满足目标。
- 对通用方法的启示：自主运行必须有可恢复检查点和版本绑定的完成定义；V 模型左侧的意图/设计可转化为右侧每个层级的可执行验证。
- 局限：
  - 25 小时实验不是效率或可靠性基准，不能从单次成功推出一般自治能力。
  - 该实例是 UI/数据模型/编辑器，长任务循环需要按领域替换工具和验证。
  - markdown 文件栈不应变成固定多文档负担；应保留“最小导航 + 按需状态”。

### 4. Testing Agent Skills Systematically with Evals

- URL：<https://developers.openai.com/blog/eval-skills>
- 日期：2026-01-22。
- 证据性质：Codex skill 评估的实践指南和小规模示例。
- 关键机制：
  - eval = prompt → captured run（trace + artifacts）→ 小组检查 → 可比较分数。
  - 同时看 outcome、process、style、efficiency；只保留少量必须通过的检查。
  - 组合 deterministic checks 与 rubric/qualitative grading；重复运行，比较版本回归。
  - 从真实失败中新增回归用例，并测试负向条件（不应触发、不应遗留文件、不应跳过步骤）。
- 对通用方法的启示：不仅评估最终代码，也评估代理是否理解契约、选择正确工具、生成可审查证据和控制无效尝试；评估集应覆盖需求→实现→验证的完整轨迹。
- 局限：
  - 文章以 skill 为对象，不能把 process score 当成软件产品质量。
  - LLM grader 需要校准，少量样例不能证明所有领域；效率指标也不应压过正确性和安全性。

### 5. Automating repetitive work at OpenAI with Codex

- URL：<https://developers.openai.com/blog/automating-repetitive-work-at-openai-with-codex>
- 日期：2026-08-25。
- 证据性质：OpenAI 内部 Runme/WebMCP 工作流的工程实践文章。
- 关键机制：
  - 把 goal、context、commands、outputs、interpretation、decisions 和 dead ends 放在同一可复核 notebook。
  - 可要求代理先写计划并等待批准；运行中记录结果；结束时保存为什么选择某方案以及下次应如何改进。
  - companion index 让过去的运行经验可被后续 agent 发现；未来运行复用已记录上下文。
  - 通过 WebMCP 直接暴露浏览器应用能力，不为工具额外引入传统服务器。
- 对通用方法的启示：把“意图—动作—结果—决策”保持在同一执行记录中，形成可复用的组织记忆；审查应针对外部副作用和高影响选择，不必审查每条命令。
- 局限：
  - 文中的流程要求“先计划、等待批准”，适合该评估工作流，不能作为所有长任务自治的统一前置门槛。
  - Runme、Google Drive、WebMCP 是承载方案，不是方法核心。
  - notebook 仍可能膨胀，应提供摘要、索引和按需展开。

### 6. Datadog uses Codex for system-level code review

- URL：<https://openai.com/index/datadog/>
- 日期：2026-01-09。
- 证据性质：OpenAI 发布的客户案例；包含客户自建的历史事故回放评估。
- 关键机制：
  - 让代理看到完整仓库、依赖和运行行为，不只看 PR diff。
  - 用历史事故贡献 PR 重放审查，再由事故负责人判断反馈是否可能避免事故；案例中约 22% 的抽样事故被认为获得了有帮助的反馈。
  - 目标从“节省 review 时间”转向“发现跨模块、跨服务、API 契约和测试覆盖风险”，人类审查者集中做设计判断。
- 对通用方法的启示：质量代理应以真实失败、回归和生产事件校准，而不是只用合成 happy path；评审信号必须与系统风险关联。
- 局限：
  - 22% 是 Datadog 的特定样本和主观确认，不能视为通用准确率。
  - 客户案例不公开全部样本、成本和未发现事故，适合提出评估方法，不适合证明产品保证。

### 7. Why Codex Security Doesn’t Include a SAST Report

- URL：<https://openai.com/index/why-codex-security-doesnt-include-sast/>
- 日期：2026-03-16。
- 证据性质：产品安全设计说明；有具体安全分析机制，但不是完整 SDLC 规范。
- 关键机制：
  - 从仓库架构、信任边界和 intended behavior 出发，而不是先把 SAST findings 当作问题清单。
  - 关注“检查是否存在”与“约束在后续转换后是否仍成立”的差别。
  - 把问题缩小为可测试切片，必要时用 micro-fuzzer、约束求解和 sandbox PoC 验证，再把高置信发现交给人。
  - 同时承认 SAST、fuzzing、runtime guards 和 agentic reasoning 各有位置，主张 defense-in-depth。
- 对通用方法的启示：V 模型右侧不应只执行静态门禁；应从左侧行为/不变量推导测试，跨转换和边界验证“系统保证是否真的成立”，并以验证结果而非检查存在性为完成证据。
- 局限：
  - 安全漏洞分析是高风险特例；普通功能开发不必每次引入形式化求解或 fuzzing。
  - “从意图开始”不能否定静态工具，静态检查仍适合低成本、确定性的大范围筛查。

### 8. Separating signal from noise in coding evaluations

- URL：<https://openai.com/index/separating-signal-from-noise-coding-evaluations/>
- 日期：2026-07-08。
- 证据性质：OpenAI 对 SWE-Bench Pro 数据集的质量审计和方法研究。
- 关键机制：

- 局限：
  - 这是 benchmark 数据集审计，不是产品交付流程；百分比不可外推。
  - 代理和人存在分类差异，仍需要训练、校准和明确升级路径。

## 对通用方法和 V 模型的综合建议

以下是研究者的综合设计建议，不是这些 OpenAI 文章共同提出或命名的方法；V 模型术语和对应关系仍应以主研究的独立软件工程来源核对。

### V 模型应表达“对应验证关系”，不是恢复瀑布式阶段

传统 V 模型的有用部分是：左侧的目标、需求、系统设计、详细设计，分别对应右侧的验收测试、系统测试、集成测试、单元/组件测试。它不应被解释成“左侧一次写完，再沿右侧一次性测试”。

适合 AI-native 的表达是：

```text
左侧：意图/价值
      ↓
    用户行为与验收条件
      ↓
    系统边界、架构和质量属性
      ↓
    组件契约与实现设计
      ↓
底部：一个可验收增量
      ↑
右侧：单元/组件 → 集成/契约 → 系统行为 → 验收/运行反馈
      └────────────── 证据回写左侧模型
```

每个增量可以只走到它需要的深度，但必须说明：

- 这次改变了左侧哪个对象；
- 对应的右侧验证是什么；
- 证据绑定到哪个代码版本和环境；
- 哪些验证缺失、为什么缺失；
- 新发现是否使原需求、设计或验收条件失效。

因此，推荐将 V 模型与持续演进结合成**增量式双向追溯 V**：

1. 从意图和风险选择一个最小可验收增量。
2. 先画足够的整体结构、行为和验收视图，识别高影响未知。
3. agent 在授权内做调查、原型、实现和多层验证。
4. 失败、运行反馈或新事实同时修正实现和左侧模型。
5. 通过证据满足当前增量后集成；跨增量再做组合行为和回归验证。
6. 对高风险变更增加独立代理/静态工具/人工判断，而不是对所有工作增加同样审批。

### 建议纳入方法的验证层

- **需求有效性**：场景、非目标、约束和验收是否一致、可理解、可检验。
- **设计一致性**：边界、依赖、不变量、质量属性是否满足；架构约束能否机械检查。
- **实现正确性**：单元、契约、属性、类型、lint 和静态检查。
- **组合行为**：集成、端到端、迁移、兼容性和真实数据/环境。
- **风险与安全**：威胁、权限、故障、资源、恢复、性能和可观测性。
- **交付与运行**：发布、回退、指标、日志、事故回放和用户反馈。
- **过程与 agent 能力**：是否遵守授权、选对工具、保留证据、可恢复且没有静默扩大范围。

这些层不是固定的审批站点。由变更风险、未知程度、外部影响和可回退性决定检查深度。

## 与现有 README 的对接提醒

当前 `README.md` 已有“系统模型、可验收增量、工作契约、渐进细化、自主执行、证据和异常升级”等骨架。OpenAI 材料支持继续保留，但建议明确三点：

1. 把 V 模型放在工程内核中，表达“设计对象与验证证据的对应关系”；不要放到 agent 执行循环旁边，避免它看起来像另一套阶段流程。
2. 把“统一入口”解释为**一个导航和证据视图**，允许底层有版本化的设计、计划、日志、测试和运行记录；不要求所有内容压在一个长文档里。
3. 将 Delegate/Review/Own、plan approval、人工 merge 等表述改为**按风险和成熟度配置的责任模式**。低风险、可回退且证据充分的工作可以自动完成；高影响方向、公共契约、生产副作用和风险接受仍需明确的人类责任。
