## 三、本轮发现的问题

### P1（首要）仓库状态与文档声明不一致

实测：

| 位置 | 状态 |
| --- | --- |
| `git ls-tree -r HEAD` | `kernel/` 6 个文件、`review-v0.6-by-claude.md`、`review-v0.7-by-claude.md` **仍然存在** |
| 工作区 | 上述文件均已删除 |
| `git status` | 8 条 ` D` 记录，**从未提交** |
| `review-v0.8-by-claude.md:4` 与文末附记 | 声称它们"已移除，不再随仓库保留" |

也就是说：**任何人 clone 这个仓库都会拿到 kernel/，与文档声明矛盾**；而本地删除意图完全没有进入 git 历史，只表现为文件凭空消失。

这正是方法 `:140` 所说"文档和代码有冲突时必须分析"的情形，只不过冲突发生在方法自己的仓库里。

处理：`git add -A && git commit`，把"移除 kernel 原型与旧评审"记为一次明确的历史。删除本身已由用户确认，不需重新决策。

### P2 场景表删减规则已立，但本轮未实际执行

`:150` 新增了删减原则，但场景数仍为 11，本轮未合并或删除任何一条。这不是错误——规则刚建立，合理的做法是下一轮开始应用。

建议在下一次修订时**实际执行一次删减检验**（哪怕结论是"全部保留"，也写明检验过），否则该规则会停留在声明状态，而这恰是方法自身反对的"只增不减"。

### P3 接受状态应记录被接受的 commit

`:189` 要求"接受后记录对应版本，将人的接受状态改为'已接受'"。但 `:5` 的状态行目前只写状态、不带版本；而"改状态"这个动作本身会产生新 commit，使被接受的版本与记录状态的版本不是同一个。

建议 `:5` 的接受状态写成带基线的形式，例如"人的接受：已接受（基线 `<commit>`）"，避免出现"接受的是哪一版"的歧义。
